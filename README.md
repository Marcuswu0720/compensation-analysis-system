# 尼日利亚薪酬人力成本分析工具

内部管理工具：上传月度原始发薪表 Excel，自动解析清洗校验，支持部门/实体成本趋势查询、
薪资类目细分看板、月度环比归因分析（含类目级拆解）、员工级薪酬明细 Excel 下载，以及关键词
匹配的问答功能。技术方案见 `PRD.md` / `PRD_V1.1.md` / `PRD_V1.2.md` / `PRD_V1.3.md` /
`PRD_V1.5.md` / `PRD_V1.6.md` / `PRD_V1.7.md` / `PRD_V1.8.md` / `PRD_V1.9.md`（如未包含，
参见项目内文档；V1.2 是对 V1.1"权限模型重构"章节的替代/细化版本，V1.3 是在 V1.2 权限模型之上
新增的下载功能，V1.5 细化了校验/下载环节并重构了归因文案，V1.6 是针对 V1.5 下载明细字段不全
问题的补课迭代，V1.7 把"环比归因"泛化成任意两个月份都能比较、并统一到"趋势查询"页面的"两点
比较"模式，"薪资类目"页面同步加了多选和两点比较，V1.8 是针对"导出字段反复缺失/错位"这一类
问题的根本性修复（字段匹配从精确字符串比对改成大小写/空格容错匹配，按用户提供的权威字段映射
文件重建三类批次的完整字段清单，修正合同工雇主社保成本的错误加总逻辑，日期字段格式修复，外加
上传阶段的字段匹配诊断），V1.9 给"薪资类目"页面加了人均口径（含中位数参考）和按用工类型拆分/
对比两个维度，复用的还是 V1.7 就建好的同一套聚合函数——见下方"使用流程"第 6 条和"已知限制"——
`PRD_V1.5.md` §0 提出的"按批次上传"架构，经跟你确认后，V1.1 起就已经是这个设计（`salary_type`
= 底薪/奖金/补发批次，独立上传、成本自动加总），不需要额外改造）。

设计原则：**计算层是确定性代码，回答只是把算好的数字套进句子模板**。所有问答类回答都来自
`backend/app/compute/` 里的确定性聚合/归因函数，`backend/app/qa/rule_engine.py` 只用正则/
关键词从问题里识别部门、月份、"为什么/环比"这类意图，不接任何外部大模型 API，免费、离线可用；
识别不出部门或月份、或用户没权限查看时会明确告诉用户，不会瞎猜、不会越权。

## 目录结构

```
backend/
  app/
    ingestion/     # 解析：sheet 匹配、字段别名映射（Formal/Contract 分别建映射）、
                   # 汇总行过滤、部门/实体名称标准化、薪资类目拆分
    compute/       # 计算：趋势聚合、类目看板、环比归因（joiners/leavers/stayers +
                   # 类目级双线拆解 + 校验）、权限范围过滤
    qa/            # 问答：正则/关键词意图识别 + 套用回答模板（不接外部 API，免费）
    routers/       # FastAPI 路由：auth / upload / query / chat / export
    models.py      # 数据表结构
    migrations.py  # 手写的 SQLite 结构升级脚本，见下方说明
    main.py        # 应用入口
  seed_admin.py    # 创建/重置管理员账号
  tests/           # 用合成数据（非真实薪酬数据）跑的回归测试
frontend/          # 纯静态页面：登录 / 上传+校验 / 趋势 / 薪资类目 / 下载明细 / 问答 / 用户权限（无需构建步骤）
```

## 本地运行

```bash
cd backend
pip install -r requirements.txt

# 配置密钥（登录会话签名用，问答功能不需要任何外部 API key）
cp ../.env.example ../.env
# 编辑 .env，把 SECRET_KEY 换成随机字符串

# 创建第一个管理员账号
python seed_admin.py marcus <你的密码>

# 启动
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

浏览器打开 `http://localhost:8000` 登录。管理员登录后能看到"用户权限"页，在那里创建其他
账号、给 viewer 账号分配可见的部门/实体范围。

## 权限模型（V1.2）

- **admin**：全部数据、全部操作（上传/确认/删除/改月份/管理权限/账号管理），个人薪资明细可见。
- **viewer**：完全只读，看不到"上传数据""用户权限"这两个页面；只能看到被授权规则覆盖的数据，
  个人薪资明细（归因里的涨跌幅最大员工姓名/工号）永远看不到。**新建的 viewer 账号默认什么都看不到**，
  必须由管理员在"用户权限"页至少授予一条规则，才能开始查看数据。
- **授权规则模型**（`backend/app/models.py` 的 `ViewerPermission`）：每条规则本身就是一个完整、
  自洽的可见范围，规则与规则之间取**并集**：
  - `entity`（整体实体）：该实体下**全部**部门都可见。
  - `entity_department`（实体下的特定部门）：只有**该实体下的该部门**可见，不会连带其他实体下的
    同名部门——比如授予 `Flexi + Credit Business`，即使 `PalmPay` 也有一个叫 `Credit Business`
    的部门，也不会被看到。这是相对 V1.1 的关键修正：V1.1 把"部门"和"实体"当成两个独立轴分别
    过滤，会导致同名部门跨实体泄露；V1.2 把每条授权规则本身变成一个已经绑定好实体的自洽范围，
    从数据结构上杜绝这个问题（详见 `compute/scope.py` 的 `apply_permission_scope`）。
- 权限判定在**后端**做（`backend/app/security.py` 的 `get_allowed_scope`/`resolve_requested_filters`
  + `compute/scope.py` 的 `apply_permission_scope`），前端只是不显示按钮/只请求应该看到的部分，
  真正的访问控制不依赖、也不信任前端——即便直接拼接 URL 调用后端接口，后端也会按角色和授权规则
  独立校验并拒绝越权请求。
- **账号管理**："用户权限"页的账号列表支持**禁用/启用**账号（`users.is_active`）：禁用后立即无法
  登录，已经登录的会话在下一次请求时也会被拒绝，但账号记录和它的历史操作日志永久保留，不会被
  物理删除——用于合规场景下"某账号什么时候存在过、当时能看到什么"的可追溯性。管理员不能禁用自己
  当前登录的账号。
- **密码**：viewer 密码由管理员统一设置/重置，viewer 本人不能自助改密（集中管控）；所有密码在
  数据库里都是 `bcrypt` 哈希存储，从不明文保存。
- **权限撤销留痕**：撤销一条授权规则是**软删除**（`is_active=False` + `revoked_by`/`revoked_time`），
  不物理删除该行，"用户权限"页可以勾选"显示已撤销的规则"查看完整的授权/撤销历史，用于薪酬争议
  等场景回溯"这个账号当时到底能看到什么范围"。
- 已有数据库从 V1.1 升级：旧的 `scope_type='entity'` 规则会自动迁移到新模型（新增
  `granted_by='migration_v1.2'` 标记）；旧的 `scope_type='department'` 规则因为不带实体信息、
  在新模型下无法安全表达，会被丢弃，需要管理员在"用户权限"页按新模型重新授权（见下方"数据模型
  改动会不会破坏已有数据库"一节）。

## 使用流程

1. **上传**（仅管理员）：选择月份 + 薪酬类型（底薪批次 / 奖金 / 补发薪资）+ 原始 Excel，系统自动
   解析并展示校验摘要（人数、成本、发现的问题：部门/实体名称新写法、汇总行过滤、缺失字段、
   未识别的 sheet、薪资类目加总对不上等）。**V1.8 起新增"字段匹配诊断"**：针对完整字段清单里的
   每一个目标字段，独立检查这次上传的表里有没有找到对应的列，全部匹配上会显示"本次解析共 N 个
   目标字段，成功匹配 N 个 ✓"，匹配不上的字段会列出具体尝试过的别名，让字段缺失问题在**上传的
   当下**就暴露出来，而不是等到几周后导出数据才偶然发现（这正是 V1.8 想解决的问题——过去至少
   出现过 5 次"导出某一列是空的"才被发现的情况）。同一个月份可以分别上传三种类型，成本会自动
   加总；同一类型再次上传只替换该类型自己的数据，不影响其他类型。
2. **确认入库前离线核对**（仅底薪批次）：校验摘要页面有一个"下载核对用Excel（分部门×分薪资类目）"
   按钮，把这次批次里的员工按 (Entity, Department1) 分组，汇总人数和六个薪资类目 + HR Cost，
   带一行合计行，供你自己拉透视表、和薪酬组的历史数据比对，确认无误后再回网页点确认。数据直接
   来自这次上传解析出的原始明细，不是重新计算。
3. **确认入库**：核对无误后点击确认，数据才正式写入统计表；点"放弃"则本次上传作废，不影响已有数据。
4. **管理已入库批次**（仅管理员）：历史记录列表默认展示**全部批次**（不再只显示最近的一部分），
   支持按状态筛选（待确认/已入库/已放弃/已被替换）。任何"待确认"状态的批次，不管是不是刚上传的
   那一次，都可以点"查看/处理"随时重新打开校验摘要并确认或放弃——不会再出现历史记录里有批次
   卡在"待确认"却点不动的情况。已确认的批次可以执行**删除**或**改月份**。两者都是**软删除**：
   数据不会被物理清除，只是打上"已删除/已被替换"标记，不再参与任何查询和归因计算，但记录本身
   连同操作人、时间、原因都保留在"用户权限"页的操作日志里，全程可追溯。改月份如果目标月份已经
   有同类型的已确认批次会被拒绝，不会静默覆盖。
5. **趋势查询**（V1.7 起加了模式切换）：部门/实体/起始月份/结束月份筛选器不变，下方新增
   "趋势模式/两点比较模式"切换，两种模式共用同一组筛选器，不用重新选一遍参数：
   - **趋势模式**（原有行为）：展示起始月到结束月之间**所有月份**的连续折线图（HR Cost + 人数）。
   - **两点比较模式**（原来独立的"环比归因"板块，V1.7 合并到这里）：只取起始月和结束月两个点，
     **不要求相邻**（可以直接选 2026-01 和 2026-03，跳过中间月份），展示完整的归因拆解——把
     "人数变化"和六个薪资类目变化作为并列的归因项，按**贡献金额绝对值从大到小排序**一起列出、
     一起显示占净变化的百分比（V1.5 起的扁平化格式，不再分"新入职/离职/留任"和"留任员工按类目
     拆解"两层，不再使用"留任员工"这类 HR 内部术语）。"人数变化"这一项会在明细里注明新入职/
     离职各自的人数和金额，但不单独拆成两个顶层归因项。所有归因项加总严格等于净变化，界面上会
     明确显示"✓ 吻合"或"✗ 不吻合需排查"。这一层之下还保留一个"按变动性质分类的补充说明"
     （底薪调整/绩效薪资波动/奖金提成变化/加班费变化，正式工+合同工人数），仅作叙事参考，金额
     以上面的归因拆解为准。正式工的底薪调整如果发生在 4 月/10 月官方调薪窗口之外，会被标记为
     异常信号提示人工核实。个人薪资明细（涨跌幅最大员工姓名）仅管理员可见。
     **两点比较模式不是重新实现了一遍归因逻辑**——点击"查询"时调的还是原来那一个 `/api/attribution`
     接口（`backend/app/compute/attribution.py` 的 `compute_attribution`），它本来就支持任意
     两个月份、不要求相邻，V1.7 只是把界面上"只能选相邻月份对比"的限制去掉、把这个能力从一个
     独立小板块搬到"趋势查询"页面的主筛选器上，避免以后归因逻辑要调整时（比如新加薪资类目）要
     同时改两处、结果对不上。
6. **薪资类目**（V1.7 起支持多选和两点比较，V1.9 加了人均口径和用工类型拆分）：
   - **类目趋势/两点比较**：薪资类目从单选改成**多选**（勾选框），可以同时看"底薪+绩效薪资+
     加班费"等任意组合，共用一组部门/实体/起始月份/结束月份筛选器（Formal 和 Contract 表字段名
     不同，解析层已经分别建好映射，见 `backend/app/ingestion/salary_components.py`）。同样有
     趋势/两点比较模式切换：趋势模式展示连续折线图+表格（每个类目一列），并可以在"绝对金额"和
     "增长百分比"两种视图间切换——百分比视图以起始月为基准（记为 0%），方便把底薪这种大类目和
     加班费这种小类目放在同一张图里比较涨跌形状而不被绝对值差异压扁；如果某类目起始月金额恰好
     是 0，百分比视图会展示"新增"而不是一个除以零的无意义数字。两点比较模式展示"类目/起始月
     金额/结束月金额/差值/涨跌幅"表格，只看这几个类目自己涨跌了多少，不做"新入职/离职/留任"这种
     人数效应拆解——那是上面"趋势查询"页面两点比较模式的职责，两个页面刻意不做成一样的东西。
   - **统计口径：总额 / 人均**（V1.9 新增）：人均 = 该类目总额 ÷ 范围内当月在职总人数，口径跟
     趋势查询页面"在职人数（含当月内离职）"完全一致。切到"人均"后会出现一个"同时显示中位数"
     勾选框（**默认不勾选**——中位数是可选的补充信息，不是每次都需要），勾选后趋势模式的图表上
     均值是实线、中位数是同色虚线，表格里也会同时列出"人均"和"中位数"两列；两点比较模式下
     "起始月/结束月/差值/涨跌幅"这组数字会对均值和中位数各出一行。这么做是为了在需要时能防止被
     均值误导：如果均值涨了但中位数几乎不动，通常意味着涨薪集中在少数人身上，不是普涨。
   - **用工类型：全部 / 仅正式工 / 仅合同工 / 正式工 vs 合同工**（V1.9 新增）：选"正式工 vs
     合同工"时，趋势模式图表里同一类目用同一个颜色、正式工实线/合同工虚线区分（而不是每条线
     配一个新颜色，避免类目一多图例认不过来）；如果同时选了较多类目（超过 4 个）又开着这个
     对比模式，界面会提示"当前展示的线条较多，建议减少类目选择以提升可读性"，但不强制限制。
     两点比较模式下用工类型对比会展示"全部/正式工/合同工"三级的树状结构（全部的涨跌是多少，
     其中正式工、合同工各自涨跌了多少），可以看出"底薪涨是因为合同工规模扩张还是正式工普调"
     这类问题——这也是内测时验证功能时意外发现的一个真实信号：某个类目"全部"的人均**下降**了，
     但正式工和合同工**各自的**人均都在**上升**，说明不是任何一类员工薪资变差，而是低薪的合同工
     占比上升拉低了整体均值（辛普森悖论的一个例子），这正是这个拆分视角要帮你避免误判的场景。
   - **实现方式**：人均/中位数/用工类型拆分都是给已有的公共聚合函数
     `compute/categories.py` 的 `get_categories_trend()` 加了 `per_capita`/`employment_type`
     两个可选参数，不是给"薪资类目"页面单独写一套计算逻辑——"正式工 vs 合同工"对比在后端也
     不是一个特殊模式，就是把这同一个函数用 `employment_type='Formal'`/`'Contract'` 分别调用
     两次，前端合并展示。这样以后如果"环比归因""趋势查询"页面也想要人均或用工类型视角，扩展
     成本很低，不需要每个页面各自实现一遍（V1.9 这次按 PRD 要求只落地"薪资类目"页面，另外两个
     页面暂不需要）。
   - **部门间横向对比**、**成本构成占比**：这两块从 V1.7 起没有改动，还是单类目/单月份，也没有
     人均/用工类型拆分。
7. **问答**：关键词匹配，不接外部 AI、免费。支持"XX部门1-6月人力成本怎么变化的"（趋势）、
   "XX部门6月为什么比5月成本高"（环比归因，同样是扁平化的归因拆解）这类问法；部门名可以用
   中文常见叫法（比如"手机分期"、"信贷"），识别不出部门/月份、或者问的是权限范围之外的部门时
   会明确说明，不会瞎猜也不会泄露越权数据。
8. **下载明细**（admin 和 viewer 都可用）：选部门/实体/月份区间 + **批次类型**（底薪/奖金/补发，
   可多选，默认全选）。可选范围**只会限定在当前账号被授权可见的部门/实体之内**——下拉框本身就
   只列出授权范围内的选项，后端过滤复用的是和网页查询完全相同的 `apply_permission_scope` 判断
   （见 `backend/app/compute/export.py`），不会另起一套按部门名字符串过滤的逻辑，避免重新引入
   V1.2 修复过的跨实体同名部门泄露问题。生成前会先检查所选"月份+批次类型"组合是否有数据，完全
   没有数据时会明确提示（比如"2026-05 的奖金批次暂无数据，可能尚未上传"），不会生成空文件。
   导出的 Excel 按批次类型分 sheet，**每个 sheet 是原始表的完整字段清单**，不再只是十几个
   "分析用"字段：勾了"底薪批次"会拆成"正式工明细"（**V1.8 起 40 个字段**，含 Entity/Employment
   Type）和"合同工明细"（**33 个字段**）两个 sheet；勾了"奖金批次"会生成"奖金明细"（**24 个
   字段**）；勾了"补发批次"会生成"补发明细"（工号/姓名/部门/金额/是否关联到底薪批次在职员工，
   补发本身就是松散的清单，不是完整薪资模板）。每个字段列的表头统一是"English Field Name（中文
   说明）"格式，没有例外（连"月份"这一个方便阅读用的辅助列也是"Month（月份）"，见
   `backend/app/ingestion/full_fields.py`——"Entity"从 V1.8 起不再算辅助列，而是三个批次模板
   自己的正式字段之一）。**导出前会做字段数量自检**（`compute/export.py` 的
   `verify_sheet_field_count`）：正式工/合同工/奖金三个结构化 sheet 如果拼出来的字段数不是
   40/33/24（辅助列不算），会直接报错"导出字段数量与规范不符，请检查"，不会像 V1.5 那样悄悄
   生成一份缺字段的文件——这是 V1.6 最核心的改动，V1.8 沿用并把数字更新为按权威映射文件重新
   核对过的 40/33/24，详见"已知限制"。**这三类批次的数据互相
   不折叠**——底薪 sheet 的 HR Cost 就是底薪批次自己的数字，不会偷偷加上奖金/补发的金额，如果
   想看某月完整实发总额，勾选对应的批次类型即可在各自的 sheet 里单独看到那部分金额。第一个
   sheet 是"说明"，写着下载账号/时间/数据范围/批次类型/保密提醒，如果范围内有月份+批次类型
   组合缺数据（但不是全部缺），也会在这里列出来，不会不声不响地漏掉。每次下载都会记录到"用户
   权限"页的"下载记录"里（下载人、时间、范围、批次类型、条数）——下载行为比网页查看更需要
   留痕，因为文件一旦下载就完全脱离系统的权限控制，之后无法收回。

## 数据模型改动会不会破坏已有数据库？

`backend/app/migrations.py` 是一个手写的 SQLite 结构升级脚本，在启动时（`main.py`）和
`seed_admin.py` 里都会自动跑一次，给已有的旧数据库补上缺的字段/表，**不会清空或覆盖已经入库的数据**。
目前处理的升级包括：给 `upload_batches` 加 `salary_type`，给员工快照表加薪资类目字段，
给四张数据表加 `is_deleted` 软删除标记，**重建**两张表以去掉旧版本的 `UNIQUE(month, staff_id)`
数据库约束（软删除之后，同一个月份的旧记录和新记录必须能共存，这个约束会拦住重新上传，
所以改成了纯应用层保证唯一性——见 `commit.py` 的"先软删除旧批次再插入新批次"逻辑），给 `users`
加 `is_active`，以及**重建** `viewer_permissions` 表把 V1.1 的 `scope_type + scope_value`
结构换成 V1.2 的 `scope_type + entity + department1 + 撤销审计字段`（旧的 entity 类规则自动
迁移，旧的 department 类规则因为不带实体信息无法安全迁移，会被丢弃并需要重新授权，见上方"权限
模型"一节）；V1.6 给员工快照表和补充薪资快照表各加了 7-11 个新字段（部门二/三级、职位、
汇报线、州、工作站点、入职日期、`full_detail_json`，补充薪资表还多了职级/成本中心/工作国家/
离职日期）；V1.8 又给补充薪资快照表加了 `employment_type`/`location` 两列（奖金批次模板自己的
员工类别字段，以及取代原来 state+work_station 两列的合并字段），全部是新增可空列，不影响旧数据
（`cost_center`/`work_country`/`state`/`work_station` 这几个 V1.6 时代猜错的列没有被删除，只是
不再写入新数据——SQLite 删列需要整表重建，这个项目的迁移原则一直是只加不删，见 `models.py` 里
的说明）。这几步都在真实数据上验证过，包括模拟你已经上传过数据、已经配置过 V1.1/V1.2 权限规则
的数据库结构做了完整的升级前后对比测试。以后模型再加字段，照着这个文件的模式加一行迁移检查就行
（这个项目没有配置 Alembic 这种迁移框架，单人使用场景够用了）。

## 待你确认的一个产品决策

PRD V1.3 §5 提出了一个悬而未决的问题：下载功能里 viewer 能看到姓名+完整明细，但网页仪表盘
（归因分析里的"涨跌幅最大员工"）目前对 viewer 是打码的。这次先按**更保守的默认值**实现：
**网页继续对 viewer 打码，下载功能单独放开**——理由是下载是一次性的、有完整审计记录的主动
操作，网页浏览是被动、无感知的持续曝光，两者风险不同，分开处理更稳妥。如果你希望网页展示颗粒度
也跟下载对齐（让 viewer 在归因页面也能直接看到姓名），告诉我一声，改动点在
`backend/app/routers/query.py` 的 `attribution` 接口和 `backend/app/qa/rule_engine.py` 的
`_format_attribution`，不涉及下载功能本身。

## 已知限制

- 权责发生制下奖金按业绩归属月拼接的完整口径（月度快照已记录 `monthly_bonus_snapshot`，
  但趋势/归因计算目前用的是现金流口径的 `HR Cost`，与 PRD 验证的基准数字一致）。
- 跨部门转岗员工的历史轨迹追溯、薪酬 benchmark 联动：留到后续版本。
- "底薪批次"文件里出现的、当前规则识别不了的新 sheet（不属于 Formal/Contract/Exits/Bonus 任何一类）
  会被标记为"未识别的sheet"且不计入统计，需要人工判断是否要在 `backend/app/ingestion/constants.py`
  里补充匹配规则，或者干脆把那个 sheet 单独存成一个 Excel，按"奖金/补发薪资"类型单独上传
  （`backend/app/ingestion/supplemental.py` 的解析规则很松，只要有工号列和金额列就能认出来）。
- `gross_salary`（税前薪资总额）取的是原始表里现成的列，不是靠"底薪+绩效+奖金+加班+其他收入"
  重新加总算出来的：真实数据里大约 1-2% 的记录这两者对不上（原始表本身的个别调整/特殊情况，
  不是解析错误），上传校验摘要会把这类记录数量报出来，供人工抽查。
- PRD V1.3 §2.2 提到"跨越权责发生制口径下奖金数据待补全的月份，要在下载文件里标注"：实际
  实现时发现"绩效薪资/奖金提成"这两列是直接来自底薪批次自身的列（`ingestion/salary_components.py`），
  一旦底薪批次确认入库就不存在"半成品"状态，不需要也无法单独标注"待补全"。真正会出现的缺口是
  ：某月存在无法关联到具体在职员工的独立奖金/补发金额（比如员工工号打错、或底薪还没上传时先传
  了奖金文件）——V1.5 起这类记录会出现在下载文件"奖金补发明细" sheet 里，"是否关联到底薪批次
  在职员工"这一列标"否"，不会计入任何人的底薪明细行，也不会被强行摊派到某个具体员工头上。
- **PRD V1.6 完成了"完整字段导出"的框架，V1.8 修正了具体字段名和一个根本性问题**：V1.6 的
  背景是 V1.1 起数据模型压根就只解析、只存了约 10 个"分析用"字段（底薪/绩效/奖金/加班/其他收入
  等），部门二级/三级、职位、汇报线、州、工作站点、考勤扣款明细等原始表里有的字段从解析那一步
  就被丢弃了，导出代码写得再对也导不出数据库里没有的东西——V1.6 建了完整字段清单
  （`backend/app/ingestion/full_fields.py`）、扩展了解析层、加了字段数量自检，但当时约 50 个
  新字段里除了早前验证过的约 10 个"分析用"字段，其余全是根据 PRD 文字描述**猜**的原始列名，
  从没有真实数据核对过。
- **V1.8 是一次根本性修复，处理了两类问题**：
  1. **字段名匹配逻辑本身的问题**：这次"姓名缺失"的直接原因，是解析层一直用"精确字符串相等"
     去认原始表头，而同一个字段的实际写法（大小写、空格、措辞）在不同批次/月份之间经常不一致
     ——这类问题在这个项目里已经反复出现过至少 5 次。V1.8 把匹配逻辑改成两层：**归一化匹配**
     （`backend/app/ingestion/header_match.py`：先去除首尾空格、压缩多余空格、转小写，再比较，
     这样"Staff Name"/"Staff name"/" Staff Name "自动被认成同一个字段，不用再为每种大小写/
     空格写法单独加别名）+ **同义词别名列表**（只用于真正换了个词的情况，比如"Resign Date"/
     "Leaving date"，这部分继续需要人工维护，但比以前短很多）。这个改动同时应用在核心字段解析
     （`parser.py`）、完整字段清单解析（`full_fields.py`）、奖金批次解析（`bonus_batch.py`）
     和薪资类目字段解析（`salary_components.py`）四个地方，不是只修了报错的那一个字段。
  2. **字段映射内容本身的问题**：这次你提供的"数据导出展示字段-映射.xlsx"是权威版本，`full_fields.py`
     里正式工（**40 字段**，含 Entity/Employment Type——之前的版本遗漏了这两个字段）/合同工
     （**33 字段**）/奖金批次（**24 字段，跟 V1.6 猜的清单不完全一样**：去掉了从没验证过的
     `PAYE`/`Bank Charges`/`Cost Center`/`Work Country`，State+Work Station 合并成了单一的
     `Location` 字段）已经按这份权威文件重建，全部标记为 `verified=True`。同时修正了一个真正
     的错误假设：**合同工的雇主侧社保成本**，V1.1/V1.5 一直以为需要自己把 NSITF+Pension ER+
     ITF+HMO 四列加总，映射文件显示合同工表其实有一个现成的 `ER COST` 列——`ingestion/
     salary_components.py` 已经改成直接读这一列，不再做那个加总（这个改动只影响导出/看板里的
     "雇主社保成本"这一个数字，底薪/绩效/奖金/加班/其他收入等其余五个类目的公式完全没动）。
  3. **日期格式修复**：入职/离职这类日期字段以前存的是完整的 `datetime`，序列化时保留了固定是
     `00:00:00` 的时间部分，导出 Excel 会显示成 `2026-03-12T00:00:00` 这种带 T 的格式——现在
     在解析入库那一步就统一格式化成纯日期字符串 `2026-03-12`（`ingestion/date_utils.py`），
     不会等到导出才发现，也不会有的地方修了有的地方没修。
  4. **上传阶段的字段匹配诊断**（详见上方"使用流程"第 1 条）：这次"姓名缺失"是导出以后才发现的，
     V1.8 加了这个诊断以后，同类问题会在上传的当下就被系统自己报出来。
- **真实文件验证补充修复（V1.8 之后的一次热修复）**：用你提供的真实 1 月份底薪文件（含
  Formal/Contract-PP/Contract-Flexi 三个 sheet）和真实奖金文件跑通完整解析链路后，发现
  Contract-Flexi 的表头跟 Contract-PP **不是同一套写法**——`Position`（PP 叫 `Job Title`）、
  `Chinese Reporting line`（PP 叫 `Reporting Line`）、`Work Location`（PP 叫 `Work Station`）、
  `Should Working Days`（PP 叫 `Working Days`）、以及话补列多了一段后缀文字——这几个字段之前
  只认 PP 的写法，导致 Contract-Flexi 这些列在导出里全是空的（值确实存在，只是没被认出来）。
  奖金批次同理：真实文件里用的是 `Staff Type`/`Position`/`Line Manager`，不是映射文件写的
  `Employment Type`/`Job Title`/`Reporting Line`。这些都已经加成第二条别名修好
  （`ingestion/full_fields.py`），并补了对应的回归测试（用真实文件的表头结构，不是凭空编的）。
  另外验证时发现，**部分历史数据是在这次修复之前上传入库的**，其 `full_detail_json`/日期字段
  已经按当时（有 bug）的逻辑写死存进了数据库——像"迟到扣款/未满月天数"这类字段，如果当月批次是
  在 V1.8 字段清单重建之前确认入库的，那次入库时根本没抓到这些值，重新导出也补不回来，**唯一
  修复方式是删除那个月的批次重新上传**；但日期字段的"2026-01-04 00:00:00"这种多余时间后缀，
  已经改成导出时二次格式化（`ingestion/date_utils.py` 的 `format_date_for_display`），不需要
  重新上传旧数据也能在下载文件里正确显示成`2026-01-04`。奖金批次里的"Job Grade"字段，经真实
  文件确认这两个真实文件本身就没有这一列（不是软件的字段匹配问题），所以校验摘要/导出里这一列
  为空是符合实际情况的，不是 bug。
- 问答是关键词匹配，不是真正的自然语言理解：只认识 `backend/app/qa/rule_engine.py` 里定义的
  月份格式（"1-6月" / "1月到6月" / "2026-01" 等）和部门中文关键词表，问法差太远会识别失败。
  以后想升级成能自由对话的版本，把 `chat.py` 换掉、接入一个大模型 API 做 tool use 就行，
  `compute/` 计算层不用改。
