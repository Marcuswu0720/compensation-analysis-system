# 尼日利亚薪酬人力成本分析工具

内部管理工具：上传月度原始发薪表 Excel，自动解析清洗校验，支持部门/实体成本趋势查询、
薪资类目细分看板、月度环比归因分析（含类目级拆解），以及关键词匹配的问答功能。技术方案
见 `PRD.md` / `PRD_V1.1.md` / `PRD_V1.2.md`（如未包含，参见项目内文档；V1.2 是对 V1.1
"权限模型重构"章节的替代/细化版本）。

设计原则：**计算层是确定性代码，回答只是把算好的数字套进句子模板**。所有问答类回答都来自
`backend/app/compute/` 里的确定性聚合/归因函数，`backend/app/qa/rule_engine.py` 只用正则/
关键词从问题里识别部门、月份、"为什么/环比"这类意图，不接任何外部大模型 API，免费、离线可用；
识别不出部门或月份、或用户没权限查看时会明确告诉用户，不会瞎猜、不会越权。

## 目录结构

```
backend/
  app/
    ingestion/     # 解析：sheet 匹配、字段别名映射（Formal/Contract 分别建映射）、
                   # 汇总行过滤、部门/实体名称标准化、薪资类目拆分
    compute/       # 计算：趋势聚合、类目看板、环比归因（joiners/leavers/stayers +
                   # 类目级双线拆解 + 校验）、权限范围过滤
    qa/            # 问答：正则/关键词意图识别 + 套用回答模板（不接外部 API，免费）
    routers/       # FastAPI 路由：auth / upload / query / chat
    models.py      # 数据表结构
    migrations.py  # 手写的 SQLite 结构升级脚本，见下方说明
    main.py        # 应用入口
  seed_admin.py    # 创建/重置管理员账号
  tests/           # 用合成数据（非真实薪酬数据）跑的回归测试
frontend/          # 纯静态页面：登录 / 上传+校验 / 趋势 / 薪资类目 / 问答 / 用户权限（无需构建步骤）
```

## 本地运行

```bash
cd backend
pip install -r requirements.txt

# 配置密钥（登录会话签名用，问答功能不需要任何外部 API key）
cp ../.env.example ../.env
# 编辑 .env，把 SECRET_KEY 换成随机字符串

# 创建第一个管理员账号
python seed_admin.py marcus <你的密码>

# 启动
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

浏览器打开 `http://localhost:8000` 登录。管理员登录后能看到"用户权限"页，在那里创建其他
账号、给 viewer 账号分配可见的部门/实体范围。

## 权限模型（V1.2）

- **admin**：全部数据、全部操作（上传/确认/删除/改月份/管理权限/账号管理），个人薪资明细可见。
- **viewer**：完全只读，看不到"上传数据""用户权限"这两个页面；只能看到被授权规则覆盖的数据，
  个人薪资明细（归因里的涨跌幅最大员工姓名/工号）永远看不到。**新建的 viewer 账号默认什么都看不到**，
  必须由管理员在"用户权限"页至少授予一条规则，才能开始查看数据。
- **授权规则模型**（`backend/app/models.py` 的 `ViewerPermission`）：每条规则本身就是一个完整、
  自洽的可见范围，规则与规则之间取**并集**：
  - `entity`（整体实体）：该实体下**全部**部门都可见。
  - `entity_department`（实体下的特定部门）：只有**该实体下的该部门**可见，不会连带其他实体下的
    同名部门——比如授予 `Flexi + Credit Business`，即使 `PalmPay` 也有一个叫 `Credit Business`
    的部门，也不会被看到。这是相对 V1.1 的关键修正：V1.1 把"部门"和"实体"当成两个独立轴分别
    过滤，会导致同名部门跨实体泄露；V1.2 把每条授权规则本身变成一个已经绑定好实体的自洽范围，
    从数据结构上杜绝这个问题（详见 `compute/scope.py` 的 `apply_permission_scope`）。
- 权限判定在**后端**做（`backend/app/security.py` 的 `get_allowed_scope`/`resolve_requested_filters`
  + `compute/scope.py` 的 `apply_permission_scope`），前端只是不显示按钮/只请求应该看到的部分，
  真正的访问控制不依赖、也不信任前端——即便直接拼接 URL 调用后端接口，后端也会按角色和授权规则
  独立校验并拒绝越权请求。
- **账号管理**："用户权限"页的账号列表支持**禁用/启用**账号（`users.is_active`）：禁用后立即无法
  登录，已经登录的会话在下一次请求时也会被拒绝，但账号记录和它的历史操作日志永久保留，不会被
  物理删除——用于合规场景下"某账号什么时候存在过、当时能看到什么"的可追溯性。管理员不能禁用自己
  当前登录的账号。
- **密码**：viewer 密码由管理员统一设置/重置，viewer 本人不能自助改密（集中管控）；所有密码在
  数据库里都是 `bcrypt` 哈希存储，从不明文保存。
- **权限撤销留痕**：撤销一条授权规则是**软删除**（`is_active=False` + `revoked_by`/`revoked_time`），
  不物理删除该行，"用户权限"页可以勾选"显示已撤销的规则"查看完整的授权/撤销历史，用于薪酬争议
  等场景回溯"这个账号当时到底能看到什么范围"。
- 已有数据库从 V1.1 升级：旧的 `scope_type='entity'` 规则会自动迁移到新模型（新增
  `granted_by='migration_v1.2'` 标记）；旧的 `scope_type='department'` 规则因为不带实体信息、
  在新模型下无法安全表达，会被丢弃，需要管理员在"用户权限"页按新模型重新授权（见下方"数据模型
  改动会不会破坏已有数据库"一节）。

## 使用流程

1. **上传**（仅管理员）：选择月份 + 薪酬类型（底薪批次 / 奖金 / 补发薪资）+ 原始 Excel，系统自动
   解析并展示校验摘要（人数、成本、发现的问题：部门/实体名称新写法、汇总行过滤、缺失字段、
   未识别的 sheet、薪资类目加总对不上等）。同一个月份可以分别上传三种类型，成本会自动加总；
   同一类型再次上传只替换该类型自己的数据，不影响其他类型。
2. **确认入库**：核对无误后点击确认，数据才正式写入统计表；点"放弃"则本次上传作废，不影响已有数据。
3. **管理已入库批次**（仅管理员）：历史记录列表默认展示**全部批次**（不再只显示最近的一部分），
   支持按状态筛选（待确认/已入库/已放弃/已被替换）。任何"待确认"状态的批次，不管是不是刚上传的
   那一次，都可以点"查看/处理"随时重新打开校验摘要并确认或放弃——不会再出现历史记录里有批次
   卡在"待确认"却点不动的情况。已确认的批次可以执行**删除**或**改月份**。两者都是**软删除**：
   数据不会被物理清除，只是打上"已删除/已被替换"标记，不再参与任何查询和归因计算，但记录本身
   连同操作人、时间、原因都保留在"用户权限"页的操作日志里，全程可追溯。改月份如果目标月份已经
   有同类型的已确认批次会被拒绝，不会静默覆盖。
4. **趋势查询**：按部门/实体/月份范围查看人数、总 HR Cost、人均 HR Cost 趋势图。
5. **薪资类目**：把 HR Cost 拆成底薪/绩效薪资/奖金提成/加班费/其他收入/雇主社保成本六个独立类目
   （Formal 和 Contract 表字段名不同，解析层已经分别建好映射，见 `backend/app/ingestion/salary_components.py`），
   支持单类目趋势、部门间横向对比、某月成本构成占比。
6. **环比归因**：选两个月份对比，先按人数维度拆解新入职/离职/留任（以及无法关联到具体在职员工的
   奖金/补发调整项）对成本变化的贡献并给出各项占净变化的百分比；再对留任员工做**双线拆解**：
   第一条线是按薪资类目（底薪/绩效/奖金/加班/其他/社保 + 无法归类的残差项）精确拆解，加总严格等于
   留任总变化；第二条线是按"底薪调整/绩效薪资波动/奖金提成变化/加班费变化"打标签的叙事说明
   （一人可能同时命中多个标签，人数和金额不能跨标签相加，仅供参考，以第一条线为准）。正式工的
   底薪调整如果发生在 4 月/10 月官方调薪窗口之外，会被标记为异常信号提示人工核实。个人薪资明细
   （涨跌幅最大员工姓名）仅管理员可见。
7. **问答**：关键词匹配，不接外部 AI、免费。支持"XX部门1-6月人力成本怎么变化的"（趋势）、
   "XX部门6月为什么比5月成本高"（环比归因，含类目拆解）这类问法；部门名可以用中文常见叫法
   （比如"手机分期"、"信贷"），识别不出部门/月份、或者问的是权限范围之外的部门时会明确说明，
   不会瞎猜也不会泄露越权数据。

## 数据模型改动会不会破坏已有数据库？

`backend/app/migrations.py` 是一个手写的 SQLite 结构升级脚本，在启动时（`main.py`）和
`seed_admin.py` 里都会自动跑一次，给已有的旧数据库补上缺的字段/表，**不会清空或覆盖已经入库的数据**。
目前处理的升级包括：给 `upload_batches` 加 `salary_type`，给员工快照表加薪资类目字段，
给四张数据表加 `is_deleted` 软删除标记，**重建**两张表以去掉旧版本的 `UNIQUE(month, staff_id)`
数据库约束（软删除之后，同一个月份的旧记录和新记录必须能共存，这个约束会拦住重新上传，
所以改成了纯应用层保证唯一性——见 `commit.py` 的"先软删除旧批次再插入新批次"逻辑），给 `users`
加 `is_active`，以及**重建** `viewer_permissions` 表把 V1.1 的 `scope_type + scope_value`
结构换成 V1.2 的 `scope_type + entity + department1 + 撤销审计字段`（旧的 entity 类规则自动
迁移，旧的 department 类规则因为不带实体信息无法安全迁移，会被丢弃并需要重新授权，见上方"权限
模型"一节）。这几步都在真实数据上验证过，包括模拟你已经上传过数据、已经配置过 V1.1 权限规则的
数据库结构做了完整的升级前后对比测试。以后模型再加字段，照着这个文件的模式加一行迁移检查就行
（这个项目没有配置 Alembic 这种迁移框架，单人使用场景够用了）。

## 已知限制

- 权责发生制下奖金按业绩归属月拼接的完整口径（月度快照已记录 `monthly_bonus_snapshot`，
  但趋势/归因计算目前用的是现金流口径的 `HR Cost`，与 PRD 验证的基准数字一致）。
- 跨部门转岗员工的历史轨迹追溯、薪酬 benchmark 联动：留到后续版本。
- "底薪批次"文件里出现的、当前规则识别不了的新 sheet（不属于 Formal/Contract/Exits/Bonus 任何一类）
  会被标记为"未识别的sheet"且不计入统计，需要人工判断是否要在 `backend/app/ingestion/constants.py`
  里补充匹配规则，或者干脆把那个 sheet 单独存成一个 Excel，按"奖金/补发薪资"类型单独上传
  （`backend/app/ingestion/supplemental.py` 的解析规则很松，只要有工号列和金额列就能认出来）。
- `gross_salary`（税前薪资总额）取的是原始表里现成的列，不是靠"底薪+绩效+奖金+加班+其他收入"
  重新加总算出来的：真实数据里大约 1-2% 的记录这两者对不上（原始表本身的个别调整/特殊情况，
  不是解析错误），上传校验摘要会把这类记录数量报出来，供人工抽查。
- 问答是关键词匹配，不是真正的自然语言理解：只认识 `backend/app/qa/rule_engine.py` 里定义的
  月份格式（"1-6月" / "1月到6月" / "2026-01" 等）和部门中文关键词表，问法差太远会识别失败。
  以后想升级成能自由对话的版本，把 `chat.py` 换掉、接入一个大模型 API 做 tool use 就行，
  `compute/` 计算层不用改。

## 测试

```bash
cd backend
python -m pytest tests/ -v
```

测试用的是合成数据（`tests/xlsx_fixtures.py` 现造的假工作簿），不包含任何真实员工信息，覆盖：
sheet 命名漂移、字段别名漂移（含 Formal/Contract 各自的薪资类目字段名）、部门名大小写归并、
汇总行过滤、月中离职仍计入当月成本、归因校验（含类目级双线拆解、异常调薪信号检测）、
多类型批次叠加与软删除/改月份/审计日志、viewer 授权规则的并集/跨实体同名部门隔离/撤销留痕、
账号禁用与密码重置等。真实数据的端到端验证已经在开发过程中人工跑通，数字与 PRD 基准完全一致，
包括对着模拟你已上传数据、已配置 V1.1 权限规则的数据库结构做过完整的迁移前后校验，但真实薪酬
文件不会被提交到仓库。
